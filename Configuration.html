Codex 設定與組態指南

從 AGENTS.md, 記憶, skills, MCP, 子代理, 到 config.toml 完整參考, sandbox 與 WSL, 一份可互動查閱的設定文件。

Customization

用專案指引, skills, MCP 與子代理自訂 Codex。自訂讓 Codex 依照你團隊的工作方式運作, 這些層彼此互補而非互相競爭。

AGENTS.md
持續性的專案指引, 定義行為規範。
Memories
從先前工作中學到的有用情境, 延續到未來任務。
Skills
可重複使用的工作流程, 封裝團隊的專業知識。
MCP
連接外部工具與共享系統的存取管道。
Subagents
把工作委派給專門化的子代理。

AGENTS.md 指引

AGENTS.md 提供跟著儲存庫走的持久性專案指引, 在代理開始工作前套用, 內容應保持精簡, 用於建置與測試指令, 審查期望, 儲存庫慣例與目錄專屬指示。當代理對程式碼庫做出錯誤假設時, 在 AGENTS.md 中修正, 並請代理更新該檔案, 讓修正得以延續, 把它當成一個回饋迴圈。

Codex 可從多個位置載入指引: 你 Codex 家目錄中的全域檔案, 以及團隊可check in 的儲存庫專屬檔案, 越靠近工作目錄的檔案優先權越高。

Skills

Skills 為 Codex 提供可重複工作流程的能力, 通常是最適合的做法, 因為能支援更豐富的指示, 腳本與參考資料, 同時保持跨任務可重複使用。一個 skill 通常是一個 SKILL.md 檔案加上選擇性的 scripts, references 與 assets。

--- name: commit description: Stage and commit changes in semantic groups. Use when the user wants to commit, organize commits, or clean up a branch before pushing. --- 1. Do not run `git add .`. Stage files in logical groups by purpose. 2. Group into separate commits: feat -> test -> docs -> refactor -> chore. 3. Write concise commit messages that match the change scope. 4. Keep each commit focused and reviewable.

MCP 與 Subagents

MCP

連接 Codex 到外部工具與情境提供者的標準做法, 適合議題追蹤系統, 設計工具, 瀏覽器或共享文件系統這類活在本機儲存庫之外的能力。伺服器可以公開工具, 資源與提示範本。

Subagents

建立具有不同角色的代理, 並用不同方式提示它們使用工具, 例如一個代理執行特定測試指令, 另一個帶有能擷取正式環境紀錄的 MCP 伺服器, 每個子代理專注於自己的工作並使用合適的工具。

建議的建置順序

1 · AGENTS.md
讓 Codex 遵循你的儲存庫慣例, 加入 pre-commit hook 與 linter 強制執行規則。
2 · Plugin 或 Skill
已有可重複使用的工作流程時安裝 plugin, 否則建立 skill, 想分享時再封裝成 plugin。
3 · MCP
當工作流程需要外部系統, 例如 Linear, GitHub, 文件伺服器或設計工具時使用。
4 · Subagents
準備好把吵雜或專門化的任務委派給子代理時使用。

Memories

ChatGPT 與 Codex 如何跨對話與任務延續有用的情境, 網頁版使用 ChatGPT memory, 本機 Codex 用戶端則使用獨立的本機記憶儲存與控制項。必要的團隊指引仍應放在 AGENTS.md 或已 check in 的文件中, 記憶只是輔助性的回憶層。

各介面的記憶控制

桌面應用程式
用 /memories 選擇任務是否可使用本機記憶或貢獻未來記憶, 於 Settings > Personalization 開關功能。
ChatGPT Work
使用帳號與工作區可用的記憶設定, 不使用本機 Codex 記憶儲存。
Codex CLI
互動式工作階段用 /memories 控制目前任務能否使用既有記憶或成為未來記憶的輸入。
IDE 擴充功能
使用已連接 Codex host 的本機記憶儲存, 啟用時採用與 CLI 相同的任務層級控制。

本機記憶如何運作與儲存

啟用記憶後, Codex 會把符合資格的先前任務中有用的情境轉成本機記憶檔案, 跳過進行中或短暫的工作階段, 對產生的記憶欄位進行密鑰編修, 並在背景更新記憶而非在每項任務結束時立即更新。記憶儲存在 Codex 家目錄的 ~/.codex/memories/ 之下, 包含摘要, 持久項目, 近期輸入與佐證證據, 應視為產生出來的狀態, 分享 Codex 家目錄前建議先檢查。

設定本機記憶

本機 Codex 記憶預設為關閉, 在桌面應用程式的 Settings > Personalization 開啟 Enable memories, 或透過設定檔啟用功能旗標。

[features] memories = true
memories.generate_memories
控制新建立的任務能否作為記憶產生的輸入。
memories.use_memories
控制 Codex 是否把既有記憶注入未來工作階段。
memories.disable_on_external_context
為 true 時, 使用外部情境 (如 MCP 呼叫或網頁搜尋) 的任務不會進入記憶產生。
memories.min_rate_limit_remaining_percent
開始產生記憶前所需的最低剩餘速率限制百分比。

隱私與安全

重要

Chronicle 使用螢幕截圖, 可能包含螢幕上可見的敏感資訊, 它沒有麥克風或系統音訊存取權, 不要用它錄製會議或與他人的溝通內容, 檢視敏感內容時請暫停 Chronicle。截圖暫時儲存於裝置上, 超過 6 小時會被刪除, 產生的記憶是未加密的 Markdown 檔案, 儲存在 $CODEX_HOME/memories_extensions/chronicle/ 之下, 使用 Chronicle 會提高螢幕內容遭提示注入攻擊的風險。

# 指定用於記憶彙整的模型 [memories] consolidation_model = "gpt-5.4-mini"

Config basics

學習設定本機 Codex 用戶端的基礎知識。Codex 從多個位置讀取設定, 個人預設值位於 ~/.codex/config.toml, 可在儲存庫加入 .codex/config.toml 做專案層級覆寫, 基於安全考量, 只有在你信任該專案時才會載入專案層級的 .codex/ 設定。

設定檔優先順序, 由高到低

1 · CLI 參數
CLI 旗標與 --config 覆寫。
2 · 專案設定檔
.codex/config.toml, 由專案根目錄到目前工作目錄, 越接近者優先, 僅限受信任專案。
3 · Profile 檔案
以 --profile profile-name 選取的設定檔。
4 · 使用者設定
~/.codex/config.toml。
5 · 系統設定
若存在, Unix 上的 /etc/codex/config.toml。
6 · 內建預設值
Codex 的預設行為。

常見設定選項

預設模型 核准提示 Sandbox 層級 Windows sandbox 網頁搜尋模式 推理強度 溝通風格 紀錄目錄

選擇 CLI 與 IDE 預設使用的模型。

model = "gpt-5.6"

控制 Codex 執行產生的指令前何時暫停詢問。

approval_policy = "on-request"

調整 Codex 執行指令時的檔案系統與網路存取程度。

sandbox_mode = "workspace-write"

在 Windows 原生執行 Codex 時, 設定原生 sandbox 模式為 elevated, 只有在沒有管理員權限或 elevated 設定失敗時才用 unelevated。

[windows] sandbox = "elevated" # 建議

cached 為預設值, 使用 OpenAI 維護的索引；indexed 只在搜尋索引允許時存取外部網頁；live 擷取最新網頁資料；disabled 關閉工具。

web_search = "cached" # 預設值

在支援的模型上調整推理使用的額度。

model_reasoning_effort = "high"

為支援的模型設定預設溝通風格, 之後可用 /personality 於工作階段中覆寫。

personality = "friendly" # 或 "pragmatic" 或 "none"

覆寫 Codex 寫入本機紀錄檔案的位置, 明確設定後會啟用選擇性加入的純文字 TUI 紀錄。

log_dir = "/absolute/path/to/codex-logs"

Advanced Configuration

當你需要對 providers, 政策與整合有更多控制權時使用這些進階選項。

Profiles

Profiles 讓你儲存具名的設定層, 並從 CLI 之間切換, 傳入 --profile profile-name 時, Codex 會先載入 ~/.codex/config.toml, 再疊加 ~/.codex/profile-name.config.toml。

# ~/.codex/deep-review.config.toml model = "gpt-5.5" model_reasoning_effort = "xhigh" approval_policy = "on-request"
codex --profile deep-review

從 CLI 一次性覆寫

# 專屬旗標 codex --model gpt-5.4 # 通用鍵值覆寫, 值為 TOML 而非 JSON codex --config model='"gpt-5.4"' codex --config sandbox_workspace_write.network_access=true

自訂模型提供者

LLM proxy Amazon Bedrock OSS 本機模式 Azure
[model_providers.proxy] name = "OpenAI using LLM proxy" base_url = "http://proxy.example.com" env_key = "OPENAI_API_KEY"
model_provider = "amazon-bedrock" model = "<bedrock-model-id>" [model_providers.amazon-bedrock.aws] profile = "default" region = "eu-central-1"
# 搭配 --oss 使用的預設本機供應者 oss_provider = "ollama" # 或 "lmstudio"
[model_providers.azure] name = "Azure" base_url = "https://YOUR_PROJECT_NAME.openai.azure.com/openai" env_key = "AZURE_OPENAI_API_KEY" wire_api = "responses"

Observability 與 telemetry

預設停用 OpenTelemetry 紀錄匯出, 可透過 [otel] 選擇加入, 追蹤 API 請求, SSE 事件, 提示與工具核准結果。

[otel] environment = "staging" # 預設為 "dev" exporter = "none" # 設為 otlp-http 或 otlp-grpc 以送出事件 log_user_prompt = false # 除非明確啟用, 否則遮蔽使用者提示

codex.sse_eventcounter依事件種類與成功與否計算的 SSE 事件數。
codex.tool.callcounter依工具名稱與成功與否計算的工具呼叫數。
codex.tool.call.duration_mshistogram工具執行耗時, 依工具與結果分類。
turn.e2e_duration_mshistogram一個完整回合的端對端耗時。
turn.token_usagehistogram每回合依 token 類型計算的用量。
approval.requestedcounter工具核准請求結果, 核准, 拒絕或中止。
mcp.callcounterMCP 工具呼叫結果。
hooks.runcounter依 hook 名稱, 來源與狀態計算的 hook 執行數。

multi_agent.spawncounter依角色計算的代理衍生數。

完整的 OTel 指標目錄涵蓋約 80 個指標, 橫跨執行時期傳輸, 回合與工具活動, 執行緒與功能, 記憶體與本機狀態, 以及 Windows sandbox 等分類, 此處列出最具代表性的一部分, 完整清單請參考原始文件的 Configuration Reference。

其他常用選項

Hooks
從 hooks.json 或內嵌 [hooks] 表格載入生命週期 hooks, 專案層級 hooks 只在該 .codex 層受信任時載入。
Metrics 與 feedback
用 [analytics] enabled = false 停用匿名使用量統計, 用 [feedback] enabled = false 停用 /feedback。
History persistence
用 [history] persistence = "none" 停用本機工作階段逐字稿, 或用 max_bytes 限制檔案大小。
Clickable citations
設定 file_opener 選擇 Codex 用來開啟引用檔案的 URI scheme, 例如 vscode。
Notifications
用 notify 陣列指定外部程式, 在 agent-turn-complete 等事件發生時被觸發。

Environment variables

Codex 支援的環境變數, Codex 用 config.toml 儲存持久性設定, 環境變數則用於 shell 範圍的覆寫, 自動化密鑰, 安裝程式行為或診斷。

變數用途說明
CODEX_HOMECLI, IDE, app-server, 安裝程式設定 Codex 狀態的根目錄, 預設 ~/.codex, 設定後該目錄必須已存在。
CODEX_SQLITE_HOMECLI 與 app-server 狀態設定 SQLite 支援狀態的儲存位置, sqlite_home 設定優先。

Subagents

在 ChatGPT 與 Codex 中使用子代理, 並設定自訂 Codex 代理。ChatGPT Work 與 Codex 可透過平行衍生專門化代理並在單一回應中彙整結果, 對高度平行的複雜任務特別有幫助, 例如程式碼庫探索或實作多步驟功能計畫。

為何子代理工作流程有幫助

情境污染與情境腐化

當探索紀錄, 測試日誌, 堆疊追蹤等吵雜的中間輸出灌入主對話, 有用資訊會被淹沒, 對話品質也會隨內容增多而下降。

子代理如何幫忙

讓主代理專注於需求, 決策與最終產出, 讓專門化子代理平行處理探索, 測試或紀錄分析, 並回傳摘要而非原始中間輸出。

把平行代理用於偏讀取的任務, 例如探索, 測試, 分類與摘要, 對偏寫入的平行工作流程要更謹慎, 因為多個代理同時編輯程式碼可能造成衝突並增加協調成本。

觸發子代理工作流程

Review this branch with parallel subagents. Spawn one subagent for security risks, one for test gaps, and one for maintainability. Wait for all three, then summarize the findings by category with file references.

選擇模型與推理強度

gpt-5.6
從這裡開始處理要求較高的代理, 適合需要規劃, 工具使用, 驗證與跟進的模糊多步驟工作。
gpt-5.6-terra
適合偏好速度與效率而非深度的代理, 例如探索, 大量讀取掃描或處理輔助文件。
gpt-5.4
當工作流程固定使用 GPT-5.4 時使用, 結合強大的程式撰寫, 推理與工具使用能力。
gpt-5.3-codex-spark
若你有 ChatGPT Pro, 在延遲比廣泛能力更重要時使用這個研究預覽模型。

agents.max_depth 控制巢狀深度, 預設為 1, 讓根執行緒可以衍生直接子代理, 但阻止那些子代理再往下衍生。

自訂代理

Codex 內建 default, worker 與 explorer 三種代理, 若要定義自己的自訂代理, 在 ~/.codex/agents/ (個人) 或 .codex/agents/ (專案) 下新增獨立的 TOML 檔案, 每個檔案必須定義 name, description 與 developer_instructions。

Rules

控制 Codex 可以在沙箱外執行哪些指令, 此功能為實驗性, 未來可能變動。

建立規則檔案

# 在沙箱外執行 gh pr view 前先詢問 prefix_rule( pattern = ["gh", "pr", "view"], decision = "prompt", justification = "Viewing PRs is allowed with approval", match = ["gh pr view 7888"], not_match = ["gh pr --repo openai/codex view 7888"], )

規則欄位

pattern
必要, 定義要比對的指令前綴。
decision
預設 allow, 可為 allow, prompt 或 forbidden, 多條規則同時符合時採最嚴格的結果。
justification
選填, 說明規則存在的理由, 會顯示在核准提示或拒絕訊息中。
match / not_match
選填的行內單元測試範例, 幫助你在規則生效前抓出錯誤。

Shell wrapper 與複合指令

當 shell 腳本是僅由安全運算子連接的純字面詞組成的線性指令鏈時, Codex 會用 tree-sitter 解析並拆成個別指令分別套用規則, 即使允許 git add, Codex 也不會自動允許 git add . && rm -rf /, 因為 rm -rf / 的部分會被獨立評估。當腳本使用重新導向, 替換, 環境變數或萬用字元等較進階的 shell 特性時, Codex 不會嘗試拆解, 而是把整個呼叫視為單一指令套用規則。

codex execpolicy check --pretty --rules ~/.codex/rules/default.rules -- gh pr view 7888

Windows sandbox

設定並排解原生 Codex sandbox 在 Windows 上的問題, 應用程式可原生於 PowerShell 中搭配 Windows sandbox 執行, 不需要 WSL 或虛擬機器。

兩種原生 sandbox 模式

Elevated, 建議

使用專屬的低權限 sandbox 使用者, 檔案系統權限邊界, 防火牆規則與本機政策變更, 是較強的原生 Windows sandbox。

Unelevated, 備援

以受限的 Windows token 執行指令, 套用以 ACL 為基礎的檔案系統邊界, 較弱但適用於管理員設定受阻的情況。

[windows] sandbox = "elevated" # 或 "unelevated"

Windows 版本支援程度備註
Windows 11建議Codex 在 Windows 上最佳的基準環境
近期且完整更新的 Windows 10盡力支援可運作但較不穩定, 需要 1809 以上版本
較舊的 Windows 10 版本不建議較容易失敗

疑難排解

原生 sandbox 設定失敗
常見原因包含拒絕 UAC 提示或機器不允許建立本機使用者群組, 可先重試 elevated 設定, 若受阻則改用 unelevated。
出現 Windows 錯誤 1385

警告某些資料夾對 Everyone 可寫入

沙箱化指令無法連上網路
